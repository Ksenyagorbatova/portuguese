# Spec — спецификация на задачу

## Зачем

Каждая задача-ветка несёт живую спецификацию в `specs/`, зеркаля имя ветки как
путь: префикс ветки (часть до `/`) — это подпапка, остальное — имя файла. То есть
`<type>/<description>` → `specs/<type>/<description>.md`.

- `feat/add-numbers-topic` → `specs/feat/add-numbers-topic.md`
- `fix/srs-interval-inflation` → `specs/fix/srs-interval-inflation.md`

Спека описывает **что и почему** сделано — намерение и решения, которые не
выводятся из диффа. Это закрывает слабое место агентской разработки: код
показывает «как», а спека фиксирует «зачем». См. раздел «Specs» в
[CLAUDE.md](../../../CLAUDE.md).

## Когда применять

- Задача завершена, или перед `gh pr create` / пушем в открытый PR.
- Пользователь набрал `/spec`.
- `pre-push` hook заблокировал push, потому что спека отсутствует или не обновлена.

Пропусти на `main` или detached HEAD (спеки — на задачу-ветку).

## Шаги

1. **Ветка:** `git rev-parse --abbrev-ref HEAD`. Если `main`/detached — остановись и спроси.
2. **Путь:** `specs/<branch>.md` — префикс ветки (до `/`) становится подпапкой.
3. **Понять изменение:** прочитай `git diff main...HEAD` (и `--stat`) — **весь дифф
   ветки**, не только последний коммит — и используй контекст сессии для «зачем».
4. **Написать/обновить** файл по разделам ниже. **Заменяй** устаревшее, не
   дописывай дубли. Описывай то, что реально вошло, а не историю попыток.
5. **Язык — русский** (рабочий язык проекта). Кратко и по фактам.
6. **Застейджить** спеку, чтобы она попала в тот же PR. По правилам репозитория
   (не коммитить/пушить в `main`; коммит — только когда просит пользователь).

## Разделы спеки

- Шапка: ветка · PR (если известен) · дата · статус
- Цель
- Изменения данных / API
- Поведение (для пользователя)
- Ключевые решения и алгоритмы
- Тестирование
- Карта файлов (добавлено / изменено / удалено)
- Известные ограничения / дальнейшие шаги

## Baseline-спеки (существующий функционал)

Уже отгруженные подсистемы документируются как baseline-спеки в
`specs/feature/*.md` (шапка: «Статус: baseline (отгружено) · <дата>»). Они —
источник правды по подсистеме; CLAUDE.md даёт краткий обзор и ссылается на них.
Когда правишь подсистему — обнови её baseline-спеку в том же PR (плюс, при
необходимости, заведи спеку самой ветки).

## Типичные ошибки

- Описывать только последний коммит вместо полного диффа `main...HEAD`.
- Дописывать вместо обновления → устаревший, задублированный текст.
- Нарратив («пробовали X, потом Y») вместо финальной спеки того, что вошло.
- Писать спеку для пуша в `main` — спеки принадлежат задаче-веткам.
