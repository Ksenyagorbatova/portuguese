# Cooldown для Dependabot-апдейтов

Ветка: `chore/dependabot-cooldown` · PR: — · Дата: 2026-06-10 · Статус: готово

## Цель

Supply-chain-гигиена: не предлагать в weekly-PR версии пакетов, вышедшие
только что. Типичная атака «угнали аккаунт мейнтейнера → залили заражённую
версию» вычищается из npm за часы/дни (инцидент `chalk`/`debug` 09.2025 —
~2 часа); cooldown отсекает это окно. До изменения Dependabot мог предложить
версию, опубликованную за час до его недельного прогона.

## Изменения данных / API

Нет (ни схемы, ни API, ни кода приложения). Только конфиг Dependabot.

## Поведение (для пользователя)

- Обычные version-апдейты npm появляются в PR не раньше, чем через **7 дней**
  после публикации версии; **мажорные** — через **14 дней** (пусть экосистема
  обкатает `.0`-релиз).
- Апдейты GitHub Actions (бампы SHA-пинов) — через **7 дней**, включая мажоры
  (асимметрия с npm — платформенное ограничение, см. «Ключевые решения»).
- **Security-апдейты cooldown обходят** по дизайну GitHub (опция действует
  только на version updates) — но это касается лишь механизма *Dependabot
  security updates*, который включается отдельным тумблером в настройках
  репозитория (Settings → Advanced Security), не через `dependabot.yml`.
  Проверить его состояние моим токеном не удалось (API отдаёт 404 — выключено
  либо нет admin-прав); **владельцу репо нужно убедиться, что он включён**,
  иначе CVE-фикс, выпущенный как обычная версия, будет ждать cooldown + weekly.

## Ключевые решения

- `default-days: 7` — перекрывает типичное время жизни вредоносной версии
  с запасом, при этом почти не задерживает обычные багфиксы.
- `semver-major-days: 14` только для npm: мажоры всё равно мёржатся вручную
  и вдумчиво; две недели дают выйти `x.0.1` с фиксами регрессий.
- Для `github-actions` опции `semver-*-days` **не поддерживаются GitHub**
  (доступны только semver-экосистемам: npm, Bundler, Cargo и т.п.) — это
  ограничение платформы, а не наш выбор. Следствие: мажоры экшенов ждут
  7 дней, не 14. Поднимать `default-days` до 14 для экшенов не стали —
  задержало бы и патч-бампы пинов; компенсация: экшены официальные/известные,
  мажор виден в PR по комментарию `# vX`, мёрж всегда ручной.
- Без `include`/`exclude` — правило одинаково для всех зависимостей.

## Тестирование

Не покрывается тестами: декларативный конфиг GitHub-сервиса, исполняется
самим GitHub, в наш тестовый стек (Vitest / convex-test / Playwright CT) не
попадает. Валидность схемы проверяет GitHub при обработке файла. Прецедент —
[`specs/chore/quality-infra.md`](quality-infra.md) (добавление самого
`dependabot.yml` без тестов). `npm run verify` и `npm run build` прогнаны
как общий гейт ветки.

## Известные ограничения / дальнейшие шаги

- Cooldown не защищает от вредоносной версии, которая прожила незамеченной
  дольше 7/14 дней — это снижение риска, не гарантия.
- **Fail-open в dependabot-core:** релиз без метаданных `released_at`
  обходит cooldown (проверка `in_cooldown_period?` возвращает `false` без
  timestamp). Для npm почти теоретично (реестр отдаёт даты), для тегов
  экшенов чуть реальнее. В YAML не чинится — поведение upstream.
- **Проверка эффекта не вакуозна только после разбора бэклога:** сейчас
  npm-лимит (5) забит открытыми PR #30–#34, новые npm-PR не появятся
  независимо от cooldown — «нет PR с молодыми версиями» ничего не докажет.
  Правильный сигнал: после мёржа/закрытия бэклога взять первый новый
  Dependabot-PR и сверить дату публикации версии (npm view <pkg> time) —
  должна быть ≥7 дней до даты PR.
- **Владельцу репо:** проверить, включены ли Dependabot security updates
  (Settings → Advanced Security) — без них обход cooldown для security-фиксов
  не работает (см. «Поведение»).
